# SmithAgents v1 Roadmap: how the spec splits into plans

**Spec:** `docs/superpowers/specs/2026-11-23-smithagents-architecture-design.md`
(section 6, Version 1). The spec covers several independent subsystems, so v1
is split into five plans. Each produces working, testable software on its own.
Plans 0, 1 and T have no dependency on each other and can run in parallel.

| Plan | Delivers | Depends on | Status |
|---|---|---|---|
| 0. CEF-in-GPUI proof | Go/no-go on embedding CEF in a GPUI dock layout on macOS, with the spec's checklist | none | not written |
| 1. Daemon foundation | `smithagentsd` + client crate: agents, chat sessions via Claude Code CLI, worktrees, events, token auth, lockfile lifecycle | none | `2026-11-24-daemon-foundation.md` |
| T. Theme system | `design/tokens/`, `themegen` (Tailwind v4 theme + GPUI theme data), live theme switching bridge, CI color check | none (extends the palette file Plan 1 creates) | `2026-11-24-theme-system.md` |
| 2. Intents and execution | Intent store and versions, seed from chat, polish passes (steering questions, proposals), review semantics, Send (new agent + worktree + brief), minimal queue with dependencies, Resolved | Plan 1 | not written |
| 3. Desktop shell and web app | GPUI panes and icon rail, CEF center tabs, web chat app (AI SDK UI stream endpoint on the daemon), intent editor with question cards and accept/review lists, agent colors, Settings (Agent defaults, Source repositories, Appearance) | Plans 0, 1, T; intent UI needs Plan 2's API | not written |

## Why this order

- Plan 0 retires the biggest technical risk (spec section 7) before any UI is
  built on it. If it fails, Plan 3's embedding approach changes (offscreen
  rendering, then docked window), and nothing in Plans 1, 2 or T is wasted.
- Plan 1 is fully specifiable now because its interfaces are ours. Plans 0 and
  3 depend on crate APIs (GPUI, gpui-component, cef) that must be verified
  against the versions in use, so they are planned just before they start.
- Plan 3 is split internally: first the chat-only shell on Plan 1's API, then
  the intent UI once Plan 2 lands.

## Plan 0 go/no-go checklist (from spec section 6, first milestone)

A CEF view embedded in the GPUI window on macOS must: sit in the center beside
native left, right and bottom panes; resize and collapse with them; render at
native resolution; take keyboard focus and IME input; coexist with native
popovers and menus; load xterm.js and react-flow pages; expose CDP on
loopback. Fallbacks in order: CEF offscreen rendering into a GPUI texture,
then a borderless native window docked to the center region; the owner is
told before switching.

## Plan T scope (from spec section 4.7, Theming)

Token files per theme in OKLCH; `tools/themegen` xtask emitting a Tailwind v4
`@theme` stylesheet with shadcn-compatible variable names and one
`[data-theme]` block per theme, plus GPUI theme data; a shell-owned
`ThemeState` (theme id, text scale, font) pushed to native panes and every
CEF view over the host bridge, delivered before first paint; v1 themes: one
dark, one light, plus System; CI check that bans literal colors outside the
token files.
